# Members, forms, moves and directory (Steps 10, 3 + 8, 20)

Read `docs/glossary.md` for Person, Owner, Renter, Resident and Member.

## People and occupancy

- Add people through `PartiesService.resolve` / `resolvePerson` (reuse by phone, then NID), not `persons.create`. A person's area is where they own, rent or live now (`PartiesService.currentPaths`); check it with `canOnParty`.
- Never send an NID to a caller who can't edit the person, and never put one in an audit row (`hasNid` only).
- `units.occupancy` is derived: call `OccupancyService.refresh(societyId, path, tx)` (property module) in the same transaction as any change to units, ownerships, tenancies or residents (occupants). Rule (Anis, 2026-10-28): `rented` while a tenancy is active or moving out; `owner_occupied` only while a resident of the owner's household (an occupant with no tenancy, such as an owner marked "Lives here") lives there; otherwise `vacant`, even when the unit or a place above it is owned. Migration `27_occupancy_residents` recomputed existing units.
- A renter who is a person is added as a resident (`occupants`, head) when the tenancy is created; owners become residents through "Lives here" (`POST /occupants` with `personId`, allowed only for a current owner at or above the unit, or the tenancy's renter).
- A registered member is a `memberships` row (numbered per society, one active per person); owners, renters and residents are not members.
- Every membership has `membership_code`, a global ID (society code + six-digit member number, `S15-000042`) set by the `memberships_set_code` trigger; never compute or write it in code (`formatMembershipCode` is for previews only). The society code and the first member number are set in Settings (`PUT /settings/membership`); a new code re-issues every ID by setting `member_no` to itself. Add members only through `MembershipsService.insert` (next number under the society lock, 409 `already_member`). Owners, renters and residents become members only when the office makes them so (`POST /memberships` with `personId`, or `POST /memberships/bulk`); never automatically. A member's fee is "paid" when they have at least one membership bill (`invoices.membership_id`, void left out) and none is open (`feeOf` in `registers.policy.ts`); it is shown only to society-wide `billing.view`.
- Users see the membership ID, never the bare member number: rows carry `membershipCode` beside `memberNo` (kept for sorting and keys), and screens, papers, CSVs and the `{memberNo}` certificate placeholder all show the ID. Bill snapshots store it (older snapshots read null).
- A party input can be `{ kind: 'existing', party: { kind, id } }` to link someone already on file (the Add tenancy form's past renters); `PartiesService.resolve` checks the id is in the society, else 404.
- The Add owner and Transfer ownership cards can pick a member by membership ID (`GET /registers/members?q=` also matches the code, part of it, or the bare member number in either digit form) and send them as `existing`; the picked member is shown read-only, since typed details for a known phone or NID are never saved over the record.
- The `requireIdNumbers` society setting (`require_id_numbers`, off unless switched on in Settings): owners, renters and members need an NID (person) or trade licence (organisation) on file. `PartiesService.requireIds` checks the stored record after `resolve` (ownerships insert and transfer, tenancies insert, memberships insert), so typed, reused and picked parties all follow it; 400 `nid_required` / `trade_licence_required`. A person found by phone with no NID gets the typed NID (same for an organisation's licence). An owner, renter or member can't have their NID or licence cleared while it's on. Residents, staff and organisation contacts are exempt. The public renter form uses `renterFormNidSchema` while it's on; `GET /society` carries the flag for the web.
- Organisations can be members (migration `29_organisation_members`): `memberships.organisation_id` beside `person_id`, exactly one set (`memberships_party_check`), one active membership per organisation, the same member numbers and IDs. `POST /memberships` takes `organisation`/`organisationId`, bulk takes `organisationIds` (numbered after the people). The public membership form takes `applicantKind`: an organisation gives its name and trade licence, the applicant is its contact (no NID needed); approval makes the organisation the member (and owner when asked). `GET /organisations/:id` carries its `membership` (active, else latest; `MemberRowsService.membership`, shared with the person page). Billing and payments take an organisation member by `organisationId` wherever they take a person member by `personId` (see `docs/rules/billing.md` and `payments.md`).
- The registers list organisation members as well: `GET /registers/members` returns them in the `person` party slot with `kind: 'organisation'` (name, the contact person's phone, no photo or verification); search by name, contact phone or membership ID works the same. A scoped caller sees an organisation member through its membership's place or anything it owns or rents in the area. The owners and renters registers show an organisation's membership ID, and "not a member" counts organisations too.
- ID copies (2026-10-29): a person's NID front and back (photos only) and an organisation's trade licence pages (photos or PDFs, at most `MAX_LICENCE_PAGES` = 10, upload order) go only through `IdCopiesService` (`src/members`): private files with a `documents` row (`entity_type` `person` / `organisation`, `doc_type` `nid_front`, `nid_back`, `trade_licence`). Every route, including the file, needs the right to edit the person or organisation (the `members` grant in their area, not `documents`), as for the NID number. A new side or a removal archives the earlier row; nothing is deleted. Uploads, removals and file reads are audited on the person or organisation. The documents library never lists, counts or serves these types (`ID_COPY_TYPES`).

## Public forms and office review

- Form files (deeds, NID copies) are private files (`docs/rules/cms-storage.md`).
- Approvals that create members data run in one transaction through `TenanciesService.insert` / `OwnershipsService.insert` and `PartiesService.resolvePerson`; change a submission's status only with a conditional update on the open statuses (`form_closed` otherwise).

## Moves and directory

- Start, complete or cancel moves only through `MovesService` (`src/members`); a tenancy's status follows its open move (`PATCH /tenancies/:id` refuses a status change while one is open). End tenancies inside a transaction with `TenanciesService.endIn`, which also cancels an open move.
- Checklist keys are fixed in shared (`MOVE_CHECKLIST`), labels in i18n. A move-out with unpaid bills on the unit needs `tenancies.approve`.
- The resident directory (`DirectoryService`) reads current `occupants` rows only; it never returns an NID.
