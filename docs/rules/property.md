# Property: location tree and units (Step 9)

- Module `src/property`: `TreeService` reads the tree (`visible`, `parentFor`, `nodes` with counts, `breadcrumb`). Call `parentFor(access, societyId, parentId, module)` before adding anything under a location.
- The deepest level holds units: a `locations` row plus a `units` row, written together only through `UnitsService`. A location may sit at any level deeper than its parent (levels can be skipped).
- `locations.name` uses the ICU collation `natural_sort` (migration `03_property`), so ordering by name is natural for Bangla and ASCII digits. Holding codes and top-level names are unique per society.
- Searches over names should try both digit forms (`digitVariants` in shared).
- `units.occupancy` is derived, never typed: call `OccupancyService.refresh(societyId, path, tx)` in the same transaction as any change to units, ownerships, tenancies or residents (occupants). Rule (Anis, 2026-10-28): `rented` while a tenancy is active or moving out; `owner_occupied` only while a resident of the owner's household (an occupant with no tenancy, such as an owner marked "Lives here") lives there; otherwise `vacant`, even when the unit or a place above it is owned. Migration `27_occupancy_residents` recomputed existing units.
- Unit types are data (`unit_types`, Step 34): `units.unit_type` holds a type's `code`, with a foreign key to the society's list. Never hardcode a type list or label; read `GET /unit-types` and show names with `unitTypeName`. Check codes from input with `UnitTypesService.assertCodes` (units, charge schedules). The five default codes come from the `unit_types_defaults` trigger on new societies; a type in use by a unit or a charge schedule can't be removed.
- The units list's area picker reads `GET /units/areas` (`units.view`, Step 35), not `/locations`, so a user with only the units permission can narrow by area. It returns areas, never units, and only inside the caller's `units` scope; the caller's top areas come from `TreeService.tops(access, societyId, module)`, which `GET /locations` uses too.
- Owners and renters on the units list come from `UnitPeopleService` (Step 35). Owners are listed at every level of the unit's chain, nearest first, because a plot, a building, a storey and a flat can each have their own. Names need `ownerships.view` or `tenancies.view` on the unit's path (otherwise null), and a search by person name or phone only matches people the caller may view, so it can't reveal anyone else's unit.
- Units list filters that reveal ownership (`missing=owner`, `ownerLives`) keep to the caller's `ownerships.view` area (`UnitPeopleService.conditions`). "Missing holding number" looks up the whole chain, because holding numbers usually sit on the plot or building.
- **Units over several floors (2026-10-29).** A unit over several floors is made only by "Join floors" in the building grid (`CombineService`): one unit from each floor of one building (`combine_same_floor`), the kept unit covers the others' floors (`unit_storeys`) and they become history. There is no hand-set "covers floors" any more. The screens never say "duplex" (Anis: the word fits homes only); they list the floors, own floor first ("On Floor 5 + Floor 6" / "৫ তলা + ৬ তলা জুড়ে"), and the grid shows "Part of 5A" on each floor it covers (`coveredBy`) unless a unit retired into it already stands there.
- **Office over several flats.** Flats on one floor, or an office over several flats, stay separate units with separate bills. The grid shows each unit's renter, else its own owner (never owners higher up), and how many units in the building that party holds (`gridHolders`); names follow `ownerships.view` / `tenancies.view` on the unit, and units retired by joining floors hold nobody.
- **Removing many (2026-10-29).** `POST /locations/remove-many` (`LocationRemovalService`, rule in `removal.policy.ts`) removes places and units picked on a place page, all or none: a picked place goes with the units straight inside it (a floor with its flats), never with places inside it (`remove_has_places`); joined units are refused (`remove_joined`); anything another record points at is refused (`remove_in_use`, names in `details.names`). "In use" is read from the catalog: every non-cascading foreign key to `locations.id` or `units.location_id`, plus documents filed under the row. Each row needs `locations.delete` or `units.delete` on its path; each removal is audited.
- **No units beside floors.** A place that already holds floors (children at the deepest level above units) takes no units of its own (`units_beside_floors`, single and bulk add). Other mixes, such as loose units on a road with plots, stay allowed.
- The property map's level picker and search use `GET /locations/search` and `GET /locations/level-counts` (`LocationSearchService`, Step 35). They cover places only, never units (units belong on `/units`), below `under` and inside the caller's `locations` area. Level chips come from `location_levels`; never hardcode level names.
